# 새 월급 검토 작업실

프로젝트 루트에서 실행한다. 기존 4190 서버가 켜져 있다면 Ctrl+C 후 재시작한다.

```powershell
.\.venv\Scripts\python.exe -m agent.dev.test_server --port 4190
```

- 홈: `http://127.0.0.1:4190/review`
- 새 검토: `http://127.0.0.1:4190/review/new`
- 자료별 상태: `/review/{review-id}/materials`
- 원문과 필드 확인: `/review/{review-id}/verify`

## 구성

`pipeline.py`의 문서 그래프가 판독 → 분류 → 추출 → 제한된 시각 재검증을 수행한다. `model.py`는 세 역할의 구조화된 모델 계약을, `registry.py`는 필드·도구 정의와 단계별 호출 정책을 관리한다. 판독 공급자는 `reading.py`에 모으며 PDF·OCR 좌표는 같은 정규화 좌표계로 보존한다. PDFium 호출은 프로세스 공통 잠금으로 직렬화한다.

`store.py`는 문서 한 개와 독립된 검토 초안·자료 연결·후보·사용자 수정 및 확정·작업 요청을 저장한다. `work.py`의 업무 그래프는 고정한 확인값을 기존 비교 스냅샷으로 변환해 기존 엔진을 실행한다. 추출값·수정값·확정값은 별도 상태이며, 입력 검증이나 모델 합의로 사용자 확정을 대신하지 않는다.

현재는 PDF·JPG·PNG, 계약서·급여명세서·근태·입금기록을 지원한다. 혼합 PDF는 페이지 범위별 논리적 자료로 나눈다. 같은 페이지 안의 복수 문서처럼 경계가 불명확한 경우에는 유형·페이지 설정이 필요하다. 다른 기간·대상·계약서를 자동으로 합산하지 않는다. 임금 계산의 지원 범위는 기존 support manifest와 PAYROLL.md를 따른다.

## 내용 확인 화면

- **필터**: 전체 / 확인 필요(추출값이 의심·충돌·보류) / 값 없음(추출 실패) / 미확정. "값 있는 항목 선택"은 현재 보이는 카드만 선택한다.
- **행 카드**: 급여명세서 지급·공제, 근태, 입금 표는 추출 에이전트가 이미 행 단위(항목명+금액)로 반환한다. `rows.py`가 저장된 원문으로 같은 행인지 결정적으로 판정해(항목명 바로 뒤 금액, 같은 행 인용 구간) 통과한 행만 한 카드로 묶는다. 판정 실패 행은 이유와 함께 칸별 카드로 남는다. 추가 모델 호출은 없으며, 묶여도 각 칸은 별도 필드로 저장·확정한다.
- **실행 기록**: 각 요청에 기능 이름·요청 시각·당시 확정값 개수를 표시하고, 완료된 최신 실행에 "최신 결과"를 붙인다.
- **실행 그래프**: 문서 처리 그래프는 열린 문서 탭의 최근(또는 선택한) 문서 작업을, 업무 그래프는 최근(또는 선택한) 업무 실행을 각각 표시한다.

## 주요 API

변경 요청에는 기존처럼 `X-Local-Agent: 1` 헤더가 필요하다. JSON 변경 요청에는 현재 검토의 `revision`을 포함한다. 오래된 버전은 409로 거절한다.

| 경로 | 동작 |
|---|---|
| `GET /api/reviews` | 검토·근무지·필드 프로필 목록 |
| `POST /api/reviews` | 저장되는 빈 초안 생성 |
| `GET /api/reviews/{id}` | 자료·필드·작업 상태와 가능한 기능 조회 |
| `GET /api/reviews/{id}/chat` | 이 검토의 대화·답변 진행 상태 조회 |
| `POST /api/reviews/{id}/chat` | 검토별 질문 저장 후 비동기 답변 시작 (202) |
| `POST /api/reviews/{id}/recommendations` | 현재 근거로 추천 분석 시작 (202), `revision` 필요 |
| `POST /api/reviews/{id}/recommendations/apply` | `recommendation_ids`의 추천만 미확정 입력값으로 적용 |
| `GET /api/review-context/{comparison-id}` | 결과·보고서 화면과 원래 검토의 연결 조회 |
| `PUT /api/reviews/{id}` | 기본 정보·확인 옵션 수정, `activate`, `confirm_basic` |
| `POST /api/reviews/{id}/documents` | PDF/JPG/PNG 원본 바이트 업로드, 자동 처리 시작 |
| `POST /api/reviews/{id}/documents/{doc}` | `retry/classify/manual/verify/locate/exclude` |
| `POST /api/reviews/{id}/link` | 기존 document_id 연결, 자동 재분석 없음 |
| `PUT /api/reviews/{id}/fields` | 필드 편집, 후보 선택 또는 보류 |
| `POST /api/reviews/{id}/fields` | 추가 항목 또는 문서 유형별 반복 행 생성 |
| `POST /api/reviews/{id}/confirm` | field_ids의 사용자 확정 |
| `POST /api/reviews/{id}/requests` | 구현된 기능 실행 요청, 요건 부족 시 대기 |
| `POST /api/reviews/{id}/requests/{request}` | 요청 취소 |
| `GET /api/reviews/{id}/documents/{doc}/pages/{n}.png` | 실제 원문 페이지 |
| `GET /api/documents/{doc}/original` | 원래 MIME의 원본 파일 |
| `GET /api/jobs/{job}` 및 `POST .../cancel`, `.../resume` | 자료 처리 작업 조회·중단·재시작 |

업로드 파일명은 `X-Document-Name`에 URL 인코딩해 전달한다. 실제 파일 서명과 내용을 검사하며 확장자만으로 형식을 인정하지 않는다. 크기는 기존 설정을 사용한다. 문서 일부의 실패는 정상 페이지나 다른 파일의 결과를 폐기하지 않는다.

## 월급 도우미

우측 하단의 고정 버튼으로 채팅창을 열고 닫는다. 홈에서는 안내받을 검토를 선택하고, 새 검토·자료 등록·내용 확인 화면에서는 현재 검토를 사용한다. 연결된 계산·결과·확인 질문·문의·보고서·용어 화면에서도 같은 대화를 이어간다. 검토를 전환하면 대화도 전환하며 새로고침 후 기록을 복원한다.

`chat.py`의 독립 LangGraph가 프로젝트 근거 조회 → 챗봇 모델 → 출처 검증 → 답변 저장을 수행한다. 현재 자료와 판독문 일부, 추출 후보·확정 상태·오류, 기능 실행 조건, 이 검토에서 실행한 최근 대조 결과와 확인 질문을 조회한다. 제외한 자료나 다른 검토의 자료는 조회하지 않는다. 현재 화면과 선택한 자료·항목도 안내 문맥에 포함한다. 조회 결과는 크기를 제한하고 생략한 자료 수를 모델에 알려 과도한 전체 분석 주장을 피한다. 기존 계산 결과의 방향·단위·최신 여부를 보존한다.

답변의 자료·필드·결과 링크는 서버에서 실제 근거 ID로 생성한다. 챗봇은 자료 수정·확정·재처리·업무 실행을 하지 않으며 사용자가 수행할 다음 단계를 안내한다. 인식 실패의 원인은 저장된 오류와 판독 근거를 바탕으로 설명하고 원본 이미지를 직접 확인했다고 주장하지 않는다. 법령 검색이나 체불 확정은 제공하지 않는다.

질문에는 `message`(1~4,000자), 클라이언트가 만든 고유 `request_id`, 선택적인 `page`·`document_id`·`field_id`를 전송한다. 같은 ID의 재전송은 중복 호출하지 않는다. 읽기 전용 대화 요청에는 검토 revision을 요구하지 않으며 검토 revision이나 기존 결과 상태를 변경하지 않는다. 질문 시점의 revision을 답변에 저장하고 입력이 바뀌면 이전 상태 기준임을 표시한다. HTTP 요청은 모델을 기다리지 않고 202로 반환하며 UI가 진행 상태를 조회한다. 서버 중단 시 답변은 중단 상태로 복구한다.

모델은 기존 `OPENAI_EXPLANATION_MODEL`·`OPENAI_API_KEY` 설정을 사용한다. 질문·최근 대화와 현재 검토의 선택된 구조화 값·판독문 일부가 모델에 전달되며 채팅에서 원본 PDF나 이미지를 전송하지 않는다. 호출마다 모델 사용량을 기록해 챗봇 그래프와 전체 토큰 합계에 포함한다. 모델 연결 실패 시 저장 상태의 기본 안내를 구분해 표시한다. 대화는 `reviews/chats/`, 실행 기록은 기존 `reviews/jobs/`에 보존한다.

## 단계별 안내와 AI 추천

작업 안내 답변은 짧은 요약과 `steps`로 저장한다. 자료 준비·원문 및 충돌 확인·값 확정·계산 및 대조·결과 검토 순서의 단계 카드에 작업, 이유, 출처 링크를 표시한다. 단계 상태와 링크는 서버가 현재 답변의 입력 스냅샷으로 검증한다. 일반 설명은 단계 없이 답변할 수 있으며 과거 일반 텍스트 대화도 그대로 읽는다. 모델 연결 실패 시 기본 안내에도 단계 카드를 제공한다.

`recommendations.py`의 독립 그래프는 문서 처리 완료 후 필요한 항목만 분석한다. 회사명은 원문을 보존하고 NFKC·공백·법인 표기·가상 자료 표식으로 비교한다. 근로자명에는 법인 규칙을 적용하지 않고 지점·사업자 식별정보의 차이는 유지한다. 금액의 원래 파서는 그대로 두며, 모호한 구분 기호의 가능한 해석은 추천 판정에만 사용한다. 같은 역할·대상·기간·단위의 명확한 근거나 기존 원본 시각 재검증 후보가 뒷받침할 때만 추천한다. 지급총액과 실수령액, 월급과 시급, 표의 다른 행은 합치지 않는다. 보강 근거가 없는 추측은 모델 응답에서도 거절한다.

기본 정보와 문서 섹션의 **AI가 채우기**는 추천을 적용하는 별도 사용자 동작이다. 추천 분석만으로 값이 채워지지 않으며 직접 수정·삭제·보류·확정한 값과 현재 편집 중인 값은 보호한다. 적용한 값은 `ai_provisional`로 남고 사용자 확정 전에는 계산에 전달되지 않는다. 확정 후에도 ‘AI 추천 후 사용자 확인’ 근거로 전달해 문서에서 그대로 읽은 값이나 직접 입력한 값으로 오인하지 않는다.

**필수 확인**은 실제 충돌을 검토 전체의 최상단에 모으며 필터와 진한 경고로 구분한다. 입력칸의 빈 표시와 별개로 원래 저장된 값·후보는 보존한다. 원문 후보나 직접 입력값 중 기준값 하나를 고르고 원문 확인 표시 후 개별 확정한다. 일반 선택·행 확정·일괄 확정으로 우회할 수 없으며 서버의 `/confirm`에서도 현재 `conflict_acknowledgement`와 개별 요청을 검증한다. 기본 정보 충돌은 `PUT /api/reviews/{id}`의 `confirm_basic_field`와 `conflict_acknowledgement`로 개별 확정한다.

`GET /api/reviews/{id}`의 `recommendation_review`에 판정·출처·추천·충돌·실행 상태를 포함한다. 추천은 원문·후보·사용자 수정·자료 구성을 반영한 입력 해시로 고정한다. 적용 요청에는 최신 `revision`과 `recommendation_ids`가 필요하며 근거 변경 후 만료한 추천은 적용할 수 없다. 이미 채운 AI 임시값의 근거가 바뀌어도 재검토·재적용 전 확정은 거절한다. 분석 중 자료가 바뀌면 오래된 결과를 게시하지 않는다. 추천 준비는 검토의 입력 revision을 바꾸지 않으며, 기존 자료를 서버 시작만으로 다시 분석하지 않는다.

추천 그래프와 챗봇 그래프는 각각 최근 실행을 표시한다. 표기 비교·근거 종합·추천 모델·추천/필수 확인 분기·사용자 적용·확정을 구분하고 실제 호출 토큰만 누적한다. 추가 추천 모델은 기존 `OPENAI_EXTRACTION_MODEL`을 사용하며 원본 이미지나 PDF를 새로 전송하지 않고 기존 재검증 근거를 재사용한다. 원본을 다시 읽으려면 기존 **재검증** 기능을 사용한다.

## 저장과 호환

기본 저장 루트는 `output/document-workspace/`다. `reviews/`에 검토·수정·확정·요청을, `reviews/jobs/`에 판독 결과·도구 호출·모델 사용량을 보존한다. 원본은 기존 `uploads/`와 `documents.json`을 확장해 보관한다. 기존 PDF 메타데이터에는 기본값을 적용해 읽는다. 검토별 잠금과 고유 임시 파일의 원자적 교체를 사용하며 단일 프로세스 개발 환경을 전제로 한다.

같은 검토의 동일 바이트 파일은 재업로드해도 새로 호출하지 않는다. 명시적인 재처리에서는 사용자 편집과 직접 지운 값을 보호하며, 새 후보가 다르면 재확인이 필요하다. 과거 확정·결과 이력은 덮어쓰지 않는다. 사용자 요청 없이 기존 자료를 재분석하지 않는다. 서버 중단 작업은 중단 상태로 복원하며 사용자가 재시작한다.

기존 엔진으로 전달하는 자료는 요청 시점의 확인값만 포함하는 독립 사례다. 하나의 PDF에서 겹치지 않는 구간은 별도 자료로 연결할 수 있다. 페이지가 겹치는 같은 파일의 중복 선택은 기존처럼 거절한다. 이미지 원본도 보고서 ZIP에 원래 형식으로 포함할 수 있다.

## 토큰 사용량과 실행 기록

새 검토·자료 등록·내용 확인 화면 맨 아래의 **에이전트 실행·토큰 사용량**에서 이 검토의 누적 입력·출력·총 토큰과 단계별 흐름을 확인한다. 재시도, 교체 전 실행과 검토에서 제외한 자료도 이미 사용한 토큰에 포함한다. 파일별 실행 기록을 펼치면 실제 호출한 모델·도구, 페이지, 호출 시각, 성공·실패 상태와 소요 시간을 볼 수 있다. 원문 판독 → 문서 분류 → 필드 추출 → 필드 검증 → 필요한 원본 재검증의 흐름을 표시하며, 사용자 확정과 계산·보고서 실행은 별도로 표시한다.

**강조해서 볼 작업**은 기본적으로 최근 작업을 따라가며, 파일 처리·재검증·대조 등 개별 실행을 선택할 수 있다. 전체 누적량과 선택 작업의 총량을 별도로 표시하고, 모델 박스 안에는 그 작업에서 발생한 입력·출력·총 토큰을 표시한다. 문서 처리, 업무 실행, 기존 `/ocr`·`/ai` 경로의 구현된 구조는 실행 여부와 관계없이 보인다. 마름모는 분기이며 파랑은 실행 확인, 노랑은 진행·확인 대기, 빨강은 실패·중단, 회색은 선택 작업의 실행 기록이 없는 경로다. `flow.py`에 구현 구조를 정의하고 실제 코드에서 도달한 분기와 호출 기록을 함께 저장한다. 업무 그래프의 네 작업은 병렬이므로 완료 순서를 직렬 경로로 표시하지 않는다.

사용량은 모델 응답의 usage 메타데이터를 기록한다. 로컬 PDF 판독·Tesseract OCR·코드 검증은 모델 토큰 0이며, 계측을 위한 추가 모델 호출은 없다. 캐시 입력과 추론 토큰은 각각 입력·출력의 부분 집합이므로 총량에 다시 더하지 않는다. 응답을 받지 못한 호출은 사용량 미확인으로 표시한다. 이전 실행의 총량은 유지하지만 과거에 저장하지 않은 단계별 토큰과 호출 순서는 추정하지 않는다. 단계별 기록은 이 변경 이후의 실행부터 제공한다.

과거 실행의 **당시 토큰 미수집**은 실패나 0토큰을 뜻하지 않는다. 당시 저장한 호출 목록으로 해당 박스의 실행은 확인할 수 있지만, 호출별 사용량과 정확한 분기·교차 순서는 복원할 수 없다. 따라서 과거 문서 처리의 연결선은 임의로 강조하지 않는다. 재분석 없이 기존 총량을 계속 확인할 수 있으며, 새 처리부터 상세 기록이 쌓인다.

자료 섹션·후보·수정 이력·실행 기록의 접기 상태는 자동 갱신과 같은 탭의 새로고침 후에도 유지한다. 기록과 사용량은 서버에, 화면의 접기 상태는 탭의 sessionStorage에 저장한다.

## 검증

```powershell
uv sync --locked
.\.venv\Scripts\python.exe -m playwright install chromium
.\.venv\Scripts\python.exe -m pytest -q agent/tests/test_review_workspace.py agent/tests/test_review_telemetry.py agent/tests/test_review_browser.py agent/tests/test_review_chat.py
```

자동 검증은 합성 자료와 고정 응답 공급자로 실행한다. 실제 모델 판독·답변 정확도와 별도로 평가해야 한다. 외부 법령 검색·벡터 DB·MCP 서버는 포함하지 않는다.
